## 3. Режимы работы и инструменты

### Локальный режим (рекомендуется для всей работы с UE)
Claude Code запущен на ПК в корне проекта. Сам подхватываются:
- `CLAUDE.md`;
- скиллы из `.claude/skills/`;
- `.mcp.json` → **Unreal MCP** (`http://127.0.0.1:8000/mcp`) при открытом редакторе.

Сборка, тесты и логи идут скриптами из `Scripts\` напрямую, без моста и без лимита в 55 секунд.

### Облачный режим
- Работа через мост: `shell` (PowerShell), `job_status`, `screenshot`. Рабочая папка shell — **не** папка проекта, поэтому пути всегда абсолютные.
  Команда дольше 55 с возвращает `job_id` → `job_status(job_id, wait_seconds=55)`.
- **Unreal MCP из облака недоступен**: он слушает только loopback. Работа с редактором (уровни, ассеты, MCP-инструменты) — только в локальной сессии.
  Поэтому в облачном режиме планируй и принимай работу, а исполнителей для UE запускай локально (шаг А5 настройки).
- Документы и наборы файлов попадают на ПК через git (`git fetch` + `git show` / `git archive` в папке с remote).
  Запись на ПК — только в папку проекта и в `The Order (Claude)`.

### Unreal MCP (UE 5.8, экспериментальный)
- Плагины `ModelContextProtocol` и All Toolsets.
- Запуск: `Scripts\ue_editor.ps1`, он стартует сервер флагом `-ModelContextProtocolStartServer`.
- Что умеет из коробки: акторы, сцена, материалы, объекты, автотесты. Свои инструменты добавляются на Python (`unreal.ToolsetDefinition`)
  или C++ (`UToolsetDefinition`), после этого в консоли `ModelContextProtocol.RefreshTools`.
- Для Claude Code у Epic есть плагин `unreal-mcp` со скиллом `create-toolset` — подключи, когда понадобятся свои инструменты.
- Вызовы MCP выполняются на игровом потоке по очереди, параллельно их не отправлять.

### Как сделать, чтобы Claude писал UE-код качественно (обязательно для исполнителей)
- **Логика — в C++**, Blueprint — только тонкие обёртки. `.uasset` бинарный: Claude не может его прочитать или сравнить версии.
- **Ассеты и уровни — Python-скриптами редактора или через MCP**, а не руками, чтобы шаги можно было воспроизвести.
- **API — из исходников движка**, а не по памяти: `Engine\Source`, `Engine\Plugins`. «Engine Source» в установке оставить включённым.
- **Свои категории логов на каждую подсистему** (`Source/CommandGame/Core/CommandLog.h`). Тесты — на всё, что проверяется без мира.
- **Пишет в репозиторий один исполнитель за раз.** `.uasset` не мёржится; параллелить можно только C++ в разных модулях.
- **Ревью после каждого спринта** — встроенный `/code-review` плюс чек-лист `ue-cpp-pitfalls`.

## 7. Правила, которые не обсуждаются

1. **LLM = голос, не мозг.** Действия юнитов — только BT / C++. LLM выдаёт только текст.
2. **Стоп-лист (ТЗ):**
   - без покупных ассетов и ручного моделинга;
   - серый UI;
   - без голоса и TTS;
   - без физического стола и голограммы;
   - без полной психологии;
   - 10×10 юнитов;
   - без экономики;
   - портреты — квадраты.

   Проверка любой новой идеи — ДИЗДОК §IV.3.
3. Данные — JSON в `Content/Data`. Логика — C++. Уровни и ассеты — скрипты или MCP.
4. На ПК автора: не удалять и не перезаписывать чужое, не трогать другие проекты и их git.
   **Без согласия автора ничего не ставить и не скачивать:** движок, нагрузки VS, плагины, MCP-серверы, модели, чужие скиллы.
5. Ключи и токены не печатать и не запрашивать в чате.
6. Отчёт — только по фактам: если тест не прошёл, так и пишешь, с цифрами и логом.

```
Вопросы: <нумерованно, или «нет»>
Следующий шаг: Спринт N+1 — жду «дальше».
```

### Как писать автору, когда нужно его действие
- Одно сообщение, пронумерованные пункты.
- В каждом пункте: **что сделать** (кнопки и пути дословно), **сколько это займёт**, **как понять, что готово**, **что написать в ответ**.
- Без вариантов «на выбор», если выбор не нужен. Если нужен — дай свою рекомендацию первой.
- После ответа автора сам проверь результат (`setup_check.ps1`, сборка, скриншот) и только потом иди дальше.
